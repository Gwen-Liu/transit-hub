# 发布说明怎么写

GitHub Release 的正文直接取自本目录的 `vX.Y.Z.md`（见 `.github/workflows/release.yml`），读者是第一次看到这个 Fork 的人。写法与鲸翼相同：像成熟开源项目的更新日志，短、准、按类分好，读完知道这一版有什么、能不能升级、怎么安装。该写法 2026-11-02 在鲸翼定下，2026-11-05 起所有 GitHub 发布都照此执行；`v0.1.19` 及更早已发布的说明不改。

## 规则

1. **结构固定**，没有内容的小节整节删掉，顺序不变：版本定位 → 一句话概述 → 新增 → 变更 → 修复 → 升级说明 → 安装 → 已知问题。
2. **一条一行**：`- **功能名**：一句话说做了什么。` 功能名用界面上的叫法（加粗），后面一句写结果，不写过程、原因和实现细节；超过两行就拆或删。修复写“修复 xx 时 yy 的问题”，一行说清现象。
3. **书面语**：不用“你”“我们”，不用“就是”“照样”“直接”“一律”这类口语，不用感叹和形容词；动词开头（新增、支持、改为、修复、移除）。
4. **只写用户看得到的变化**：内部重构、测试、文档、脚本和 CI 不写；同一件事只写一条。
5. **升级说明**只写影响升级决定的事：能否只替换应用、数据库是否自动迁移、数据是否保留、需要手动做的步骤、默认行为变了什么、怎么回滚。
6. **安装**只放命令和备用办法。镜像归档的校验和由发布工作流生成为附件 `SHA256SUMS`（说明文件在打标签前提交，写不进摘要），所以安装命令第一步就是校验。
7. **标题**由工作流生成为 `TransitHub vX.Y.Z`，正文不再写一级标题；第一行用引用块写版本定位。版本号仍以 `defaultAppVersion` 和 `scripts/verify-release.mjs` 为准，正文必须出现完整版本号（校验脚本会检查）。
8. 写完对照上一版的说明和本版的提交核对一遍：没漏用户看得到的改动，也没写进没发的东西。
9. 不写 AI 署名，不写“由 AI 生成”；提交信息同样不加 `Co-Authored-By` 等 AI 署名。

````markdown
> 基于上游 TransitHub `<上游版本>` · Linux amd64 镜像

<一句话概述这一版的重点，不超过两行。>

### 新增
- **<功能名>**：<一句话>。

### 变更
- **<功能名>**：<一句话>。

### 修复
- 修复 <场景> 时 <现象> 的问题。

### 升级说明
- 从 `<上一版>` 升级只需替换应用容器；启动时自动 <迁移内容>，原有数据保留。
- <默认行为变化或需要手动做的步骤>。
- 回滚：切回保存的旧应用镜像，<旧版本对新增结构的处理>，不需要恢复数据库。

### 安装
```bash
sha256sum -c SHA256SUMS
docker load -i transithub-vX.Y.Z-linux-amd64.tar.gz
```

- 导入后镜像名为 `transit-hub:vX.Y.Z`；已有部署先备份配置、数据库、Redis 和附件，再只替换应用容器。
- 其他架构按 [README](https://github.com/gwen-liu/transit-hub/blob/main/README_CN.md#部署) 从源码构建。

### 已知问题

````
